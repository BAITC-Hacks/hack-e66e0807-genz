# Граф денег — план MVP на 60 минут

Дата: 2026-09-23. Статус: предложение для следующего этапа разработки, реализация не начата.

## Цель и изученные материалы

AML-аналитик получает воспроизводимый список приоритетных клиентов и может объяснить любой результат через наблюдаемые переводы, структуру связей и ограничения выборки. Все выводы — гипотезы для проверки.

Изучены `FINANCE-CASE/case.md`, `additional.md`, текст `README.docx`, стартовый код и его README/requirements, корневой requirements и приложенные рекомендации по GSD. Два субагента независимо разобрали требования и стартовый код. Parquet не открывались, код на данных не запускался. Числа ниже взяты из ТЗ, а не подтверждены измерением.

В рабочем дереве уже удалены прежние `.planning/*` и `AGENTS.md`. Этот план не восстанавливает их и не означает инициализацию полного GSD-проекта.

## Выбранный подход

Рекомендуется Python + pandas/pyarrow + NetworkX и автономный HTML-отчёт на Pyvis с небольшим собственным шаблоном. Три CSV и HTML создаются одним запуском. Интерфейс работает без API, базы данных, авторизации и внешнего LLM. Ресурсы JavaScript/CSS включаются локально; отсутствие обращений к CDN проверяется отдельно.

Альтернативы: Streamlit удобен для загрузки файлов и интерактивных форм, но добавляет сервер и зависимости; отдельный React/API-проект даёт больше контроля над интерфейсом, но увеличивает объём интеграции. Для часового лимита выбираем HTML. Новый набор входных файлов загружается через параметр CLI с путём к папке.

Планируемый пользовательский запуск после установки зависимостей: `python3 -m solution --data FINANCE-CASE/data --out output`. Команды пока не существуют. README будет содержать отдельно установку и одну команду полного расчёта. Реальные пути к входным файлам проверить на этапе исполнения.

Поток: три parquet → проверки → полный направленный граф → признаки и сообщества → роли и приоритет → CSV и HTML → автоматическая проверка результатов.

## Что обязательно входит в MVP

1. Воспроизводимый локальный расчёт всех выходов менее чем за 300 секунд на предоставленном наборе.
2. Роль, оценка, кластер и объяснение для каждого входного gid, включая изоляты. По ТЗ ожидается 2248 узлов.
3. Шесть поддерживаемых ролей с формальными критериями. Не заставлять алгоритм искусственно выдавать каждую роль.
4. Кластеризация и описание каждого сообщества.
5. Топ не менее 20 узлов, поиск любого gid, направление переводов, переключение окраски по роли/кластеру, карточка с объяснением и связями.
6. README с запуском, порогами, ограничениями и масштабированием до миллиона узлов; диаграмма; сценарий пятиминутного демо.

Не включать до прохождения этих пунктов: LLM-чат, обучение ML, авторизацию, облачные сервисы, полный перебор циклов и сложную симуляцию удаления узлов. Использование AI оценивается в технической части, но AI-ассистент в самом кейсе опционален. Основной MVP не зависит от внешнего AI API.

## Контракты и границы модулей

Исходные материалы в `FINANCE-CASE` не изменять. Новая реализация — в `solution/`.

- `data.py`: загрузка и проверка трёх таблиц; проверка колонок, типов, уникальности gid/пар, ссылочной целостности, положительных сумм и согласованности агрегаций.
- `features.py`: граф, сначала содержащий все `nodes.gid`, затем рёбра; таблица признаков с уникальным индексом gid.
- `analytics.py`: сообщества, правила ролей, приоритет и числовые объяснения. Использует только согласованную таблицу признаков и граф.
- `report.py`: HTML из готовых результатов; не пересчитывает роли и приоритет.
- `__main__.py`, `outputs.py`: оркестрация, три CSV, дополнительные данные для карточек и отчёт валидации.

Контракт признаков фиксируется до параллельной реализации: `gid, depth, is_seed, in_degree, out_degree, in_sum, out_sum, pass_through, boundary_censored, seed_ancestors, betweenness`. Недоступный `pass_through` внутри расчёта допускает null; обязательные выходные поля — нет. `seed_ancestors` — число различных seed, из которых узел достижим по направлению переводов, исключая сам узел.

Обязательные CSV, без переименований и дополнительных обязательных колонок:

| Файл | Колонки |
|---|---|
| nodes_roles.csv | gid, role, role_score, cluster_id, priority_score, evidence |
| clusters.csv | cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis |
| top_nodes.csv | rank, gid, role, priority_score, why |

`evidence` непустой, до 200 символов. Скоры конечные и в диапазоне [0,1]. gid сохраняется как int64 в CSV; в данных браузера передаётся строкой, чтобы избежать потери точности больших идентификаторов. Для карточки можно отдельно сохранить полные метрики и ограничения в JSON.

## Аналитический baseline

Пороги ниже — исходное предложение, не вывод из ещё не исследованных parquet. Финальные значения фиксируются в конфигурации и README после первого расчёта; нельзя подбирать их под заранее выбранные gid.

Граф направленный и взвешенный суммой переводов. Степени считают разных контрагентов. Отношение наблюдаемого выхода ко входу не называется балансом или долей фактически удержанных денег.

Кластеры: Louvain на неориентированной проекции, вес пары равен сумме переводов обоих направлений. Для кластеризации исключить петли, сохранив их в исходной статистике. Изолятам назначить отдельные кластеры. Фиксировать random seed, порядок узлов и стабильную нумерацию кластеров. Внутренний оборот считать по исходным направленным рёбрам один раз на ребро. Гипотезы кластеров строить шаблонами по преобладающим ролям и концентрации переводов.

Для структурного посредничества использовать невзвешенные направленные пути и приближённый расчёт с фиксированной выборкой не более 128 источников. Суммы переводов не передавать как длины путей.

Предложение правил, применяемых сверху вниз при пересечении:

| Роль | Исходное правило |
|---|---|
| coordinator | достижим от ≥2 seed; связан с ≥2 другими сообществами; положительное посредничество не ниже 90-го процентиля положительных значений |
| consolidator | ≥3 входящих контрагента, наблюдаемый вход ≥75-го процентиля положительных входов; для не-seed глубины <4 отношение выхода ко входу ≤0,5; для seed/границы только структурная гипотеза с пониженным скором |
| distributor | ≥5 исходящих контрагентов и исходящая степень ≥2×max(1, входящая степень) |
| transit | не-seed, depth<4, вход и выход положительны, отношение выхода ко входу в [0,8; 1,2] |
| terminal | не-seed, depth<4, вход положителен, наблюдаемый выход ≤10% входа; формулировка только «кандидат в конечные получатели в пределах выборки» |
| peripheral | остальные, включая изоляты и узлы с недостаточными признаками |

Для `role_score` использовать прозрачную шкалу силы правила, а не вероятность: основной порог даёт 0,6; два дополнительных подтверждающих условия по 0,15. Дополнительные условия: coordinator — ≥3 других сообщества и ≥3 seed-предка; consolidator — ≥5 плательщиков и вход ≥90-го процентиля; distributor — ≥10 получателей и выход ≥75-го процентиля; transit — ≥2 контрагента в каждом направлении и отношение в [0,9; 1,1]; terminal — нулевой наблюдаемый выход и вход ≥75-го процентиля. Процентили считаются по положительным значениям соответствующей метрики. Для peripheral использовать отдельный консервативный скор 0,2 и объяснение недостатка признаков. Для гипотез, существенно зависящих от ненаблюдаемых потоков seed или границы, максимум 0,5. У `peripheral` низкая уверенность означает недостаток информации, а не доказанную безопасность. Сам факт seed не является правилом роли.

Приоритет считать отдельно: 0,30×R(seed_ancestors) + 0,25×R(in_sum) + 0,20×R(betweenness) + 0,15×R(in_degree+out_degree) + 0,10×R(out_sum). R — процентиль среди положительных значений, нулю соответствует 0; если положительное значение единственное, ему соответствует 1. Приоритет — порядок проверки, не вероятность преступной деятельности. Ограничения полноты показывать рядом, не скрывая потенциально значимый граничный узел. Равные значения сортировать по gid.

Объяснение содержит сработавшее правило и наблюдаемые числа. В карточке видны все значения и пороги; формулировки «признаки», «кандидат», «необходима проверка».

## Экран аналитика

- Слева — топ-20, поиск gid и фильтры роли/кластера.
- В центре — направленный граф. По умолчанию читаемое окружение первого узла топа; доступны переключение кластера и обзор сети.
- Справа — роль, приоритет, входящие/исходящие суммы, контрагенты, объяснение, глубина и предупреждение о неполноте.
- Поиск охватывает все входные gid независимо от текущего фильтра; выбранный узел и его непосредственные соседи доступны целиком. Изолят виден отдельным узлом с пояснением.
- Обзор может ограничивать видимые связи для скорости, но явно показывает ограничение и не лишает доступа к данным через поиск/таблицу.
- Стрелки обозначают направление, легенда раскрывает цвета; предусмотрены неизвестный gid, отсутствие связей и пустой фильтр.
- Ссылки на три CSV работают из локальной папки отчёта.

## Цикл GSD и распределение часа

Адаптация GSD к лимиту: краткий контракт → один разбор плана → параллельная реализация → общий verifier → исправление конкретных пробелов. Не запускать все рекомендованные аудиты, внешние модели и многораундовое исследование до первого работающего результата. Это план сокращённого процесса, а не утверждение о пройденных GSD-гейтах.

| Время от старта реализации | Действия | Выход |
|---|---|---|
| 0–5 мин | Оркестратор фиксирует контракты, пороги, зависимости и команды; быстрый plan-check | Однозначные задачи и синтетические примеры |
| 5–25 мин | Три исполнителя параллельно: данные; аналитика; интерфейс | Первый сквозной расчёт CSV и HTML |
| 25–40 мин | Интеграция реальных результатов, поиск и карточки; README пишется параллельно | Полный обязательный сценарий |
| 40–52 мин | Проверки контрактов, повторный запуск, замер времени, просмотр в браузере без сети | Проверенный MVP либо конкретный список блокеров |
| 52–60 мин | Резерв на исправления, подготовка демо; бонус только при зелёных проверках | Сдаваемая версия |

Оркестратор владеет CLI, exports, зависимостями, интеграцией и README. Агент A владеет `data.py`, `features.py`, их тестами; агент B — `analytics.py` и тестами правил; агент C — `report.py`, шаблоном и тестами отчёта. Все работают по контракту на синтетических входах, чтобы не ожидать друг друга. Не редактируют чужие файлы и не отменяют чужие изменения. После реализации освобождённый слот используется для независимого verifier. Не более двух попыток исправления одной проблемы без пересмотра подхода.

Полный GSD-bootstrap, если он выбран при продолжении, должен создавать новое состояние осознанно, учитывая уже удалённую `.planning`, а не молча восстанавливать старый roadmap. Для дальнейших итераций сохранять контракт, результаты проверки и оставшиеся пробелы после каждого этапа.

## Приёмка

- Входные и выходные множества gid совпадают; нет дубликатов; для предоставленного набора сверить 2248 узлов.
- Все обязательные поля заполнены; роли допустимы; score ∈ [0,1]; evidence ≤200 символов.
- Все cluster_id существуют; сумма n_nodes равна числу входных узлов; n_seed согласован с nodes; внутренний оборот пересчитан независимо.
- Топ содержит ≥20 уникальных gid, последовательные ранги и убывающий приоритет, совпадающий с nodes_roles.
- Проверить агрегацию transactions по src/dst: и суммы с денежным допуском, и количества совпадают с edges. Стартовый код сейчас проверяет только пары.
- Синтетические графы покрывают шесть правил, их пересечения, seed с нулевым входом, изолят, обрыв depth=4, взаимные переводы и отдельные компоненты.
- Узел depth=4 без выхода не становится terminal только из-за отсутствия исходящих.
- Два запуска с одинаковыми входами и конфигурацией дают одинаковые CSV; время полного расчёта <300 секунд.
- В браузере найти произвольный gid, граничный узел и изолят; открыть связи, карточку, кластер и CSV; подтвердить работу без CDN и отсутствие ошибок JavaScript.
- Проверить установку по README в чистом окружении и зафиксировать фактически испытанные версии зависимостей.
- README содержит критерии, ограничения, диаграмму, масштабирование и пятиминутный сценарий разбора 2–3 узлов, выбранных алгоритмом.

## Риски и развитие после MVP

В ТЗ несогласованы числа компонент: 2248−1877=371, а заявлено 352 узла вне крупнейшей компоненты. Разница равна 19 изолированным seed; это возможное объяснение, а не проверенный факт. Пересчитать на этапе работы с данными, не подгонять результат.

Для depth=4 исходящие не наблюдаются; у seed и всей выборки неполон входящий поток; переводы ниже 5000 KZT, другие банки и периоды отсутствуют. Нет размеченных ролей: нельзя заявлять accuracy или калиброванную вероятность. Суммарный оборот сети не равен объёму уникальных преступных денег.

Первое улучшение после MVP — признаки временного транзита по transactions: поступления и исходящие в окне 1–2 дней, с явным указанием, что это совпадение во времени, а не доказанное прохождение тех же денег. Затем оценка недостающих данных и следующий запрос аналитика. LLM-помощник добавляется позже поверх проверенных метрик и ссылок на gid.

Масштабирование до ~1 млн узлов описать без реализации: пакетная агрегация и колонночное хранение, более экономный графовый движок, приближённые центральности, расчёт по компонентам, выдача окружения узла по запросу вместо передачи всего графа браузеру.
